## 完整重跑

需要先单独检查软件和点云接口时，运行：

```bash
./run_acceptance.sh --checks-only
```

该模式使用同一批次清单，在第一组完整飞行或实际故障之前停止，不启动飞机。已完成的软件检查记入批次进度；之后运行不带参数的入口，从后续飞行继续，无需重跑已完成的前置检查。`--prepare-only` 则只准备清单，连软件检查也不执行。

## 查看与停止

另一个终端可以执行：

```bash
./run_acceptance.sh plan
./run_acceptance.sh status
./run_acceptance.sh stop
```

`plan` 只列验收范围，不启动程序。`status` 分别显示完整验收总进度和当前剩余队列进度、复用来源、项目日志和结果目录。例如五项前置检查已验证复用、首组飞行尚未通过时，显示“验收总进度（含已复用项目）：5/30”“当前队列完成：0/25”；0/25 只是剩余执行清单的计数，不表示原检查或历史记录被删除。历史版本的成功飞行另列，不直接计为修复版通过。`stop` 请求当前一个步骤完成及收尾后停止，不中断当前飞行；前台按 Ctrl+C 也采用相同方式，需要等待当前步骤结束。

只准备实际命令清单而暂不开始：

```bash
./run_acceptance.sh --prepare-only
```

生成 `manifest.json` 与 `jobs.json` 后，再运行不带参数的入口即可启动。尚未启动时，`state.json` 不存在是正常现象。

## 失败与续跑

一项失败就停止，保留失败任务、评分、地图、录包和该次日志，不会循环重试，也不会继承历史成功状态。修复后再次执行：

```bash
./run_acceptance.sh
```

同一批次从未完成步骤继续。接口／回放／报告重试使用新目录，旧失败输出保留；每次步骤日志单独保留，当前日志不会混入旧的通过文字。`checkpoints.json` 分别记录飞行实现依赖、各项检查依赖和结果文件摘要；不能仅凭旧的完成计数跳过已丢失或被改动的证据。工具更新不再因为整个 `scripts/` 的汇总指纹变化而强制重开所有检查。补验在独立的 `check_updates/` 小队列执行，失败时主队列进度保持不变；下一次仍先完成补验，之后再飞行。

需要主动创建新的续跑清单时，可使用：

```bash
./run_acceptance.sh --new
```

新批次重新核验上一批的证据，保留仍与当前版本一致的飞行、故障及软件／接口检查；`--fresh` 则全部重跑。依赖未变的五项前置检查可以跨批次复用，不因新建清单而重做。真正修改共享飞行程序后，旧飞行可能需要复验，这与验收工具更新区分处理。缺少依赖基线且程序已变化的旧批次不能安全自动迁移，此时需 `--new` 重新核验。需要指定目录时使用 `--output /绝对路径/验收批次目录`；同一参数也可用于 `status` 和 `stop`。
